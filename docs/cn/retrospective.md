# DevTool：一次高复杂度工程探索及其复盘

[English](../retrospective.md) · [中文文档目录](index.md) · [源码](https://github.com/ThinkerQAQ/DevTool)

**截至 2026 年 10 月：实验性项目，已暂停主动开发，不保证生产可用。**

这份记录用于解释项目试图解决什么问题、已经沉淀了哪些工程实现，以及还有哪些问题没有得到解决。它不是正式版本发布说明，也不是生产可用性承诺。

## 最初的问题

能否在不重造 Git、LSP、代码搜索引擎、容器运行时和构建工具的前提下，为开发者、AI Agent 和 CI 提供统一、理解项目上下文的工程控制面？

传统做法是各个客户端分别集成每种工具，重复处理配置、能力发现和编排。DevTool 尝试增加一层**薄控制面**：对上提供稳定的意图级能力，对下通过声明式配置切换 Provider。

## 保留下来的技术实践

| 领域 | 探索与实现 | 边界 |
| --- | --- | --- |
| 项目生命周期 | Project Extension 的 inspect/build/verify/package、自举流程 | 仍依赖外部构建和运行环境 |
| Provider 解耦 | Service Contract、TOML Profile 和可替换实现 | 不同 Provider 的行为并不完全一致 |
| 代码智能 | CodeGraph/Sourcegraph 索引检索与 Serena/LSP 实时语义协作 | 取决于所选工具是否可用、索引是否新鲜 |
| Agent 接入 | 意图级 MCP 网关，复用官方 Go MCP SDK | MCP 接口本身无法保证 Agent 决策安全 |
| 文档与图表 | Markdown、Mermaid、PlantUML 上下文能力 | 需要兼容的外部 Provider |
| 受控修改 | 基于上下文、一次性授权的限定范围 Git Patch | 不等于通用安全保证 |
| 构建验证 | 候选版本构建、验证、打包及激活/回滚路径 | 开发流程不等于成熟发布体系 |

具体能力与边界请参考[架构概览](architecture/overview.md)、[CLI 文档](reference/cli.md)、[配置参考](reference/configuration.md)。最终以源码和测试为准。

## 为什么难度很高

1. **抽象边界难以确定**：统一能力既不能抹平不同工具的独特价值，也不能让 Core 充满对特定 Provider 的特殊判断。
2. **代码上下文难以统一**：代码索引与实时 LSP 解决不同问题，时效性、延迟和失败方式并不相同。
3. **Agent 的能力和安全不是一回事**：暴露 MCP 工具只是入口，还必须考虑上下文、凭据、权限以及具有副作用的操作。
4. **跨环境一致性困难**：宿主机、远程服务、容器和不同项目的依赖、生命周期有明显差异。
5. **集成收益与维护成本的矛盾**：如果抽象过度，控制面的复杂性可能超过直接使用现有工具。

这些是项目范围内真实存在的工程权衡，**不是已经验证的停更根因结论**。

## 结果与未完成部分

仓库积累了相当数量的实验性实现，但**没有达成最初设想中完整、稳定、普适的工程平台目标**。版本标记仍是 `0.1.0-dev`。项目曾归档，后来为了保留技术成果和补充记录而取消归档。

以下是**尚待解决的产品化问题**，不是既有功能保证：

- 不同机器、不同 Provider 下可重复的一键部署和初始化体验。
- 配置足够简单、失败路径清晰的默认使用流程。
- 持续维护的正式发布与兼容性策略。
- 系统化安全审计、实际环境验证和外部使用证据。
- 证明统一控制面的收益值得其长期集成和维护成本。

目前不承诺稳定安装、长期兼容、持续更新或生产支持。

## 为什么保留项目

它仍有研究与展示价值：**Minimal Core、可替换 Provider、声明式组装、意图级 Agent 能力**。即使整个系统不适合直接投入使用，其中的接口设计、实现和测试也值得查阅。

一个项目没有实现最终产品目标，不等于探索过程中没有形成工程成果。这里如实保留成果和局限，不把未完成的实验包装成成功产品。
